## 设计核心宗旨

将 IF 阶段取指从由寄存器直接无延迟获取值，变为从 SRAM 中获取值（但承担 SRAM 的一周期延迟的代价）。这个 SRAM 与数据使用的 SRAM 作为同一个 SRAM，实现冯诺依曼架构。

## 背景

请你为这个五级流水 CPU 项目实现一个新的分支版本，做为 rv32i_cpu_von_neumann_withoutbonus 保存：现在已有这个文件，是没有 bounus 的纯净版版本，直接在其上完成更改，不要重新构建文件。

目前为 harvard 架构，需要将其更新为冯诺依曼架构。原来数据从 data.hex 读入，其不含开头 0x，存储在 SRAM 中；而指令从 test_program.txt 中读入，其包含开头 0x，通过 init_memory 后存储在一个 RegArray 中。test_program.txt 和 data.hex 均为同时包含了数据和指令的文件，只有开头有无 0x 标识符的区别。

现在将这个 CPU 改为冯诺依曼架构：只保留一个统一的 SRAM，不保留 instruction_memory 这个 RegArray。取值和取指全部从这个统一的 SRAM 中进行，初始化时也只从 test_program.txt 中进行。

## 具体设计

### 仲裁器

使用 downstream 构建，可以在 IF 和 MEM 执行完后同周期的获取他们的读取请求。

优先保证 MEM 的读取请求。

对于 MEM 阶段的写入请求也应该进行处理。

在此阶段调用程序唯一的一次 sram.build() 操作。

需要传输给下一个周期的 IF 阶段：是否正确获取了指令？

### IF 阶段

如果上一个周期仲裁其正确获取了指令，那么和原来一样，将 sram dout 中的内容作为指令放到 instructions 中，并和原来一样通过 if_id_instruction 向 ID 阶段传输指令。

否则，阻塞向 ID 阶段指令的传输（不能传输 NOP 指令，发送信号让下一个周期的 ID 停下）。同时 pc 不应该变动。

### MEM 阶段

所有内容应不受影响：仲裁器全力保证 MEM 阶段的正常运行：MEM 阶段发起的读入请求，一定在下个周期可以从 dout 看到，保证 WB 的正确性。同时 RAW 冒险的延迟分析也应保持一致。

### ID,EX 阶段

现在由于 IF->ID 可能出现阻塞：因此注意控制信号：如果上一个周期上一个阶段没有向其传输内容，那么这一个周期就什么都不执行，同时不向下一个阶段传输内容，只是发送阻塞指令。

### 对于 pc 跳转的处理

即 jal,jalr,B系列 指令的 next_pc 不一定为 pc + 4。

之前 pc 的计算全部在 EX 阶段完成，发现不对后，会由 HarzardUnit 清空 ID 和 EX 阶段。

现在同理处理，新的 pc 指令返回 IF 阶段，试图发起请求。同时这个开始发起请求的周期，视作当周期没有指令向 ID 传输。

请仔细分析这个周期的时序。

### 对于其他数据冒险

请确保程序的设计保证 MEM,WB 阶段的时序和之前一致，不受影响。

那么其余数据冒险的时序处理应该和原来保持一致。仍然由 HazardUnit 处理。

## 注意事项

对于 sram 的使用以及 downstream 的使用，可以参考 assassyn 设计文档与示例。

程序暂时不考虑怎么设计 bublle 数更少。不要设计前递机制与分支预测器。
